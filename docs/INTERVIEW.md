# 面试讲解稿

> 目标：让面试官在 3 分钟内听懂"你做了什么、为什么这么做、做成了什么样"。
> 所有数字都可以当场跑出来复现（`python scripts/demo.py`）。

---

## 1. 一句话版本（电梯里说）

> 我把跨境电商运营 SOP 里的 7 个 Agent 做成了一套可运行的平台：
> 数字由确定性工具算、输出用双契约卡死、合规用代码护栏拦截、
> 广告和评论的诊断会真正回流去改素材并复测。
> 不需要 API key 就能完整跑通，57 个测试 + 10 条回归评测守着。

## 2. 90 秒版本

**背景（20s）**

> 跨境运营的难点不是不知道要做什么，而是同样的 SOP，新人做出来的下限很低：
> 价格带靠拍脑袋、标题超字符、参数和实物不符、改完也不知道有没有用。

**做法（40s）**

> 我参考一个开源的 7-Agent 方法论，把它工程化成了可运行平台，核心是三件事：
>
> 第一，**数字不让模型猜**。CR4、HHI、价格带波谷、盈亏价、券余量，13 个确定性工具先算好，
> Agent 只负责解读，Prompt 里明确写了"这些数字必须原样使用"。
>
> 第二，**双契约**。输入少一个字段直接 422，输出多一个字段校验失败并自动重试；
> 再叠一层代码护栏：标题超长自动截断，命中禁用词直接禁止发布。
>
> 第三，**真闭环**。广告诊断出 P0、评论归因出修补项，会变成可追溯的 FeedbackEvent，
> 驱动 Listing 出新版本，然后用第二窗口数据复测——演示里 ROAS 从 2.96 回到 6.90。

**结果（30s）**

> 全链路 5 个 Agent 并行跑完 0.2 秒，31 项自检全过；
> 57 个测试、10 条 golden 评测（含 2 条"必须失败"的负向用例）；
> 换真实模型只改 3 个环境变量，业务代码零改动。

## 3. 五分钟版本（按这个结构讲）

### 3.1 为什么做（30s）

先把"参考项目是什么"讲清楚：它是一个 Prompt 工具箱，交付物是文档，价值在把老手的判断规则结构化。
我做的是它的**工程化落地**——因为面试官关心的是"你能不能把 Agent 做成系统"，而不是"你会不会写 Prompt"。

### 3.2 整体架构（60s）

> 四层：接入层（FastAPI + 控制台）、编排层（RunEngine 状态机）、执行层（AgentRuntime）、能力层（工具 + Prompt + Provider）。

强调两个依赖方向的设计：

- 执行层不依赖 FastAPI，所以 `scripts/demo.py` 能在没有 HTTP 的情况下跑全链路；
- Agent 只依赖 `chat()` 一个方法，所以换模型不动业务代码。

### 3.3 三个核心设计（150s）

**① 确定性优先**

举 `unit_economics` 的例子，当场写公式：

```text
net = P·(1 − 14%佣金 − 2%支付 − 12%广告 − 5%券) − (1250 采购 + 120 物流)
盈亏价 = 1370 / (1 − 0.28 − 0.05) = 2044.78
目标价（净利 15%）= 1370 / (1 − 0.28 − 0.05 − 0.15) = 2634.62
券余量 = 395.19 → 最多还能让 15%
```

> 这三个数不是模型说的，是脚本算的；模型只负责把"为什么定 2634"讲成人话。

**② 双契约 + 三级护栏**

- 输入契约：竞品少于 3 条 → 直接失败（`test_contract_failure_marks_run_failed`）；
- 输出契约：`extra=forbid`，多字段即失败，带错误信息重试一次；
- 护栏：超长标题 repair、禁用词 block、溯源率低 warn。

> 为什么护栏必须是代码：Prompt 里写"请注意合规"，模型可能忽略；代码不会。

**③ 闭环是版本化的**

讲清楚 FeedbackEvent → v2 → 复测这条链，以及"旧版本 superseded、新版本记录 applied_feedback"。
强调这是它和"一次性生成工具"的分界线。

### 3.4 工程细节（60s）

- 并行：03/04/05 三路线程池，SQLite 写锁串行化；
- 崩溃恢复：启动时把 stale `running` 标 failed，可重试；
- trace：llm / tool / guardrail 三类 span 同一条时间线，带 token 与成本；
- 评测：2 条负向用例，专门防"数据不够时编答案"。

### 3.5 结果与反思（60s）

- 数字：57 tests、10/10 eval、31 checks、0.2s、~$0.006/次；
- 反思：mock provider 是取舍——它保证了确定性和离线可跑，但文案受知识库限制；
  真实模型下文案质量取决于模型，而契约/护栏/闭环链路完全一致。

## 5. 高频追问与回答

### Q1：这和直接用 ChatGPT 写 Listing 有什么区别？

> 三个区别：数字可复核（工具算，不是模型估）、格式可强制（契约 + 护栏）、效果可验证（闭环复测）。
> 直接用 ChatGPT 得到的是一次性文本；这里得到的是带 checks、带版本、带回流记录的资产。

### Q2：怎么防模型幻觉？

> 四层：① 输入契约挡掉数据不足；② 证据由脚本预计算，Prompt 禁止改写数字；③ 输出 `extra=forbid`；
> ④ 事后护栏做数值/字符/像素复核。最后还有评测里的负向用例兜底。

### Q3：输出不符合 Schema 怎么办？

> 把 Pydantic 的错误原文回灌给模型，带上"只输出 JSON"的指令重试一次；
> 还失败就运行失败并记录原文。**不允许降级成"差不多能用"**，因为下游要按字段消费。

### Q4：为什么不用 LangGraph / LangChain？

> 这个场景是 7 个固定步骤 + 一条回流边，图能力用不上。
> 自研状态机约 300 行，可读、可测、依赖少；如果要做动态规划、多 Agent 自由对话，我会选 LangGraph。
> 我的取舍是：**编排复杂度要匹配业务复杂度**。

### Q5：工具调用死循环怎么防？

> `max_steps` 上限（2~3 轮），超过直接抛错；每次调用都进 trace，成本可归因。

### Q6：闭环的"复测数据"哪来的？

> 演示里是预置的第二窗口数据，模拟平台回传；生产环境应由平台 API 按日回填。
> 引擎的对比逻辑（before/after/verdict）不依赖数据来源，这是有意的解耦。

### Q7：成本怎么控？

> 单次全链路约 13.9k token、$0.0063；控制手段：证据预计算减少 Prompt 长度、
> 工具轮次上限、结构化输出减少无效重试、平台级成本看板。

### Q8：怎么保证葡语质量？

> 三重：Prompt 要求母语表达不许翻译腔；商品知识库给 native 文案做 few-shot；
> 评测里用"标题是否为残词""是否命中禁用词"这类可验证指标兜底。
> 真正的质量还得靠母语人工抽检，这一点我不吹。

### Q9：并发和性能？

> 03/04/05 线程池并行；单次流水线 0.2s（mock）。瓶颈在 LLM 时延，不在编排。
> 多机部署需要把线程池换成任务队列（Celery/RQ），接口不变。

### Q10：怎么评测一个 Agent 好不好？

> 三层：硬指标断言（字符/范围/角色齐全）、负向用例（该失败必须失败）、
> 线上指标（checks 通过率、护栏分布、人工驳回率）。改 Prompt 先跑 golden，掉分不许上线。

### Q11：真实模型下效果不达标怎么办？

> 先看是哪一层：契约失败（改 Prompt/加例子）、数字错（工具口径）、文案差（换模型/加知识库）、
> 合规差（加护栏）。trace 能定位到具体 span，不用猜。

### Q12：为什么用 SQLite？生产怎么办？

> 演示零依赖；SQLAlchemy 模型没有 SQLite 特性，换 PG 只改 `DATABASE_URL`。
> 并发写用全局锁串行化，这是 SQLite 的限制，也是我明确写进文档的代价。

### Q13：mock provider 算不算造假？

> 不算，它是"规则型 Agent"：数字来自真实工具，文案来自商品知识库，输出同样过契约和护栏。
> 它保证 CI 与演示的确定性；真实模型是同一套运行时换个 provider。

### Q14：怎么加第 8 个 Agent？

> 四步：契约 → Prompt → 注册表（输入适配 + 证据工具 + 工具白名单）→（可选）工具与测试。
> 引擎、API、控制台、评测都按注册表驱动，不用改。

### Q15：护栏会不会误杀？

> 会，所以分三级：能修的 repair、该拦的 block、存疑的 warn。
> 比如参数"溯源率低"只 warn 不 block，因为可能来自合法的人工补充；只有"与事实冲突"才 block。

### Q16：Prompt 怎么版本管理？

> 当前跟代码一起走 git；下一步会把 Prompt 提到独立注册表，带版本号并绑定评测结果，
> 这样能回答"v3 比 v2 好在哪"。

### Q17：为什么价格带要找"波谷"？

> 因为正面拼头部主推价，新店没有评论和权重优势；波谷是"供给密度局部最低但仍有成交"的带，
> 进入成本最低。口径写死在 `market_metrics` 里，可复算。

### Q18：这个项目你最大的取舍是什么？

> 是"确定性优先"。它让数字可复核、可测试，但牺牲了模型的开放式推理——
> 比如新类目没有知识库时，mock 只能给通用文案。我认为对运营场景这个取舍是对的：
> **运营要的是稳定下限，不是惊艳上限**。

### Q19：如果给你三个月继续做？

> 优先级：① 平台 API 适配（真实数据回流，闭环才有生产价值）；
> ② Prompt 注册表 + 评测门禁自动化；③ 跨项目记忆（同类目的历史诊断复用）；
> ④ 多租户与权限。前端和部署不是瓶颈。

### Q20：你在这个项目里最想被记住的一点？

> "能算的别让模型猜，能测的别靠感觉。"
> 从工具口径到契约到护栏到评测，整条链路都是围绕这句话设计的。

## 8. 不要说的话

- 不要说"7 个 Agent 全自动，不需要人"——审批闸门是设计的一部分；
- 不要把 mock 说成"已经接了真实模型"；
- 不要承诺"ROAS 一定提升 2 倍"——那是演示数据的复测结果，不是通用结论；
- 不要背架构图，讲**为什么这么分层**。
