# 设计问答

这份文档记录"为什么这么设计"，以及每个取舍付出的代价。
需要按层看整体结构，请读 [架构与设计决策](ARCHITECTURE.md)；需要接口细节请读 [API 参考](API.md)。

---

## 1. 为什么可验证性放在第一位？

三个环节决定了产物能不能被复核：

| 环节 | 只靠生成的后果 | 这里的做法 |
|---|---|---|
| 数字 | 估算结果无法复核，出错也定位不到 | 确定性工具计算，公式在代码里，可单测、可复算 |
| 格式 | 靠 Prompt 约束，偶发不满足且难以发现 | 双契约 + 代码护栏，不满足即失败或修复 |
| 效果 | 一次性产物，无法归因 | 版本化产物 + 诊断回流 + 第二窗口复测 |

区别不在"谁写得更好看"，而在**结果能不能被校验、被追溯、被迭代**。

---

## 2. 怎么防模型幻觉？

四层，从输入到输出逐层收紧：

1. **输入契约**：数据不足直接拒绝（例如竞品少于 3 条无法计算集中度），不进入模型；
2. **证据预计算**：CR4、HHI、盈亏价、CPA 上限等全部由工具先算好，Prompt 明确"这些数字必须原样使用"；
3. **输出契约**：`extra="forbid"`，多一个字段即校验失败，带错误原文重试一次；
4. **事后护栏**：字符长度、参数溯源、像素规格、视频时序、漏斗口径逐条复核，区分 repair / block / warn。

最后还有一道保险：评测里放了 2 条**负向用例**，数据不足时必须失败而不是给答案。

---

## 3. 模型输出不符合 Schema 怎么办？

把 Pydantic 的错误原文回灌给模型，要求"只输出 JSON 对象、严格按 schema"，重试一次（`MAX_ATTEMPTS`）。
两次都失败则该步骤失败、运行失败，并保留模型原文。

不做"降级成差不多能用"——下游按字段消费，字段对不上宁可没有，也不能错。

---

## 4. 为什么不用 LangGraph / LangChain？

这个场景是 **7 个固定步骤 + 一条回流边**，图编排能力用不上。
自研状态机约 400 行，可读、可测、依赖少；而且执行层不依赖 FastAPI，`scripts/demo.py` 能在没有 HTTP 的情况下跑完整链路。

如果要做动态规划、多 Agent 自由对话、条件回边很多，会用成熟的图编排框架。
取舍原则是：**编排复杂度要匹配业务复杂度**。

---

## 5. 工具调用死循环怎么防？

- 每个 Agent 有 `max_steps`（2~3 轮）上限，超过直接抛 `tool_loop` 错误；
- 每次调用都记 trace span，参数键、耗时、失败原因都能归因；
- 成本按 token 计费并聚合到运行级与平台级指标，异常放大能在看板上看到。

---

## 6. 闭环里的"复测数据"从哪来？

演示与测试使用预置的第二窗口数据，模拟平台按日回传；
生产环境应由平台 API 定时回填到 `ad_rows_after`。

引擎的对比逻辑（before / after / delta / verdict）不依赖数据来源，这是有意的解耦：
接入真实回传时只换数据源，不改判定逻辑。

---

## 7. 成本怎么控？

单次全链路约 14.6k token、约 $0.0066（按 `.env.example` 的单价配置）。控制手段：

- 证据预计算，减少 Prompt 里的重复上下文；
- 工具轮次上限 + 输出失败重试上限；
- 结构化输出减少无效往返；
- 平台级成本看板（`/api/metrics/overview`）按 Agent 归因。

---

## 8. 葡语文案质量怎么保证？

三重约束 + 一句实话：

- Prompt 要求母语表达，禁止翻译腔；
- 商品知识库提供 native 文案作为 few-shot；
- 评测用可验证指标兜底（标题是否被截成残词、是否命中禁用词、前 30 字符是否含核心词）。

可验证指标能挡住"明显不合格"，挡不住"合格但平庸"。真正的质量仍需要母语人工抽检。

---

## 9. 并发与性能

- 03 / 04 / 05 只依赖 02，用线程池并行执行；
- 持久化用全局写锁串行化（SQLite 单写者），Agent 执行仍然并行；
- 单次流水线在 mock provider 下约 0.15 s，瓶颈在真实模型时延而不在编排。

多机部署时需要把线程池换成任务队列（Celery / RQ / 云队列），引擎接口不变。

---

## 10. 怎么评测一个 Agent 好不好？

三层：

1. **硬指标断言**：字符数、枚举取值、四角色齐全、价格单调、P0 动作必须带 SLA；
2. **负向用例**：该失败时必须失败（缺竞品、费率不可达）；
3. **线上指标**：checks 通过率、护栏分布、人工驳回率、单次成本。

改 Prompt / 换模型先跑 golden suite，通过率下降就不合并。

---

## 11. 真实模型下效果不达标，怎么定位？

按层排查，trace 能直接指到具体 span：

| 现象 | 优先看 |
|---|---|
| 输出契约失败 | Prompt 是否给了足够的字段说明与示例 |
| 数字与预期不符 | 工具口径（工具单测是否覆盖该场景） |
| 文案质量差 | 模型能力 / 知识库 few-shot 是否覆盖该品类 |
| 合规命中率高 | 护栏规则是否过严，或 Prompt 未给出可用替代表达 |

---

## 12. 为什么用 SQLite？生产怎么办？

演示与单机部署零依赖；SQLAlchemy 模型没有使用任何 SQLite 特有语法。

换 PostgreSQL 只需改 `DATABASE_URL` 并安装驱动：

```bash
pip install "psycopg[binary]"
export DATABASE_URL="postgresql+psycopg://user:pass@host:5432/crossborderops"
```

代价要写清楚：SQLite 是单写者，并发写靠全局锁串行化，高并发写入场景必须换库。

---

## 13. mock provider 对评测有什么影响？

它是**规则型实现**：数值来自真实工具，文案来自商品知识库，输出同样过契约与护栏，与真实模型共用同一个运行时。

带来的好处有三个：CI 与本地开发不依赖外部服务；回归评测有确定性基线；"模型能力"和"工程质量"解耦。
真实模型是同一套运行时换个 provider，契约、护栏、闭环链路完全一致。

---

## 14. 新增第 8 个 Agent 要改哪些地方？

四步，引擎 / API / 控制台 / 评测都不用改：

1. `app/agents/contracts.py`：定义输入 / 输出模型，注册进 `CONTRACTS`；
2. `app/agents/prompts.py`：写五段式系统 Prompt；
3. `app/agents/registry.py`：加 `build_input` + `evidence` + 工具白名单（必要时加 `gates`）；
4. 需要新算法时在 `app/tools/` 加一个 `@tool` 纯函数并补单测。

---

## 15. 护栏会不会误杀？

会，所以分三级：

- `repair`：能自动修的（标题超长按词边界截断、主图文字清空）直接修，记录修复事件；
- `block`：只有"禁用词""参数与事实冲突""亏损却无 P0 动作"这类硬问题才拦；
- `warn`：溯源率偏低、字幕语速偏快、样本量小等存疑项只记录，交给人判断。

判定标准写在 `app/agents/gates.py`，每条都能对应到具体业务后果，不做"看起来不对就拦"。

---

## 16. Prompt 怎么版本管理？

当前与代码同仓、同 commit，靠 golden suite 把"改坏了"挡住。
下一步计划把 Prompt 提到独立注册表并绑定评测结果，这样能回答"v3 比 v2 好在哪一条用例上"。

---

## 17. 为什么价格带要找"波谷"而不是头部价格？

新店没有评论和权重优势，正面拼头部主推价是以短击长。
波谷的定义是"SKU 密度局部最低、但仍有成交"的价格带——进入成本最低，且不是无人区。
口径写死在 `market_metrics` 里，可复算、可单测。

---

## 18. 这个系统最大的取舍是什么？

**确定性优先**。它让数字可复核、可测试、可回归，但牺牲了模型的开放式推理：
新类目没有知识库时，mock 只能给通用文案。

对运营场景这个取舍是成立的——运营要的是稳定下限，不是惊艳上限。
如果目标是创意探索（例如新品人群假设），应该换一套"发散优先 + 人工筛选"的流程，而不是改造这套。
